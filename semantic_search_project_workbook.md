## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

## 3. Эксперименты по улучшению

Для каждого эксперимента фиксируйте:

- гипотезу;
- изменения относительно базового пайплайна;
- результат по метрикам,
- вывод — считаем результат удовлетворительным или нет.

Каждый эксперимент должен быть залогирован в MLflow.

**Идеи для экспериментов (выберите и дополните своими):**

- другой шаблон `product_text`;
- другая модель эмбеддингов;
- гибридный поиск — комбинация лексического и семантического;
- предобработка текста — лемматизация, удаление стоп-слов для TF-IDF;
- изменение параметров векторизации.

Все эксперименты — на train (700 запросов), который здесь играет роль валидации: на нём выбираются вес гибрида и финальная конфигурация, test отложен до финальной проверки. Каталог оценки 4 256 карточек, порог `relevance ≥ 2`, K ∈ {1, 3, 5, 10}. Значимость различий проверена парным bootstrap по запросам (2 000 ресемплов, 95%-й интервал). Baseline — `semantic_e5_small`: NDCG@10 0.578, Recall@10 0.790, MRR 0.700, Precision@5 0.274, HitRate@10 0.914.

**Эксперимент 1. Гибридный поиск (RRF)**
- Гипотеза: ошибки подходов разного характера — лексика сильна на брендах и редких точных терминах («зуавы», «cop copine»), семантика — на типе товара и синонимах («кожаные» ↔ «натуральная кожа»). Объединение выдач поднимет NDCG@10 и MRR.
- Что меняем: только способ формирования выдачи — Reciprocal Rank Fusion по рангам baseline-поисков (k = 60, по 100 кандидатов), вес семантики `w_sem` ∈ {0.3, 0.5, 0.7, 0.8, 0.9}. RRF выбран вместо суммы скоров, потому что шкалы несопоставимы (TF-IDF 0–0.3, e5 — 0.84–0.90).
- Результат (метрики): `w_sem = 0.8` — NDCG@10 0.607, Recall@10 0.799, MRR 0.679, Precision@5 0.283, HitRate@10 0.916. При `w_sem = 0.3` гибрид хуже чистой семантики по всем бинарным метрикам.
- Вывод: гипотеза не подтверждается на бинарных метриках. Recall@10 +0.009 не значим, MRR −0.020 значимо хуже. Прирост NDCG@10 (до +0.031) — артефакт пулированной разметки: в топ-10 растёт доля кандидатов с оценкой 1 (24.8% → 36.5%), а доля релевантных не меняется (17.6% → 17.8%). В диапазоне 0.7–0.9 Recall@10 не различается, MRR и NDCG@10 меняются в противоположные стороны; `w_sem = 0.8` — компромисс для эксперимента 4.

**Эксперимент 2. Модель эмбеддингов bge-m3**
- Гипотеза: семантика даёт основное качество, но ошибается внутри категории и на брендах; более сильная retrieval-модель `BAAI/bge-m3` (лучшая среди кандидатов на MIRACL) поднимет Recall@10 и MRR.
- Что меняем: только модель эмбеддингов (e5-small → bge-m3, 568M, CLS-pooling, без префиксов, лимит 512 токенов).
- Результат (метрики): NDCG@10 0.556, Recall@10 0.754, MRR 0.650, Precision@5 0.251, HitRate@10 0.891.
- Вывод: гипотеза отклонена — bge-m3 хуже по всем метрикам, и это не смещение пула (состав топ-10 почти такой же). Тексты карточек и запросы очень короткие (медиана 20 токенов и 2 слова), преимущество bge-m3 на длинных документах здесь не проявляется, а модель в 5 раз больше и кодирует каталог оценки около 35 минут на CPU.

**Эксперимент 3. Шаблон текста: категория всегда (3a) и метки атрибутов (3b)**
- Гипотеза: в baseline-тексте («Кроссовки. Adal. черный») модель не знает роли полей и путает бренд с названием или цветом; явные метки помогут различать бренд и цвет и поднимут Recall@10 и MRR.
- Что меняем: только текст для эмбеддингов, в два шага (по замечанию ревью): 3a — категория всегда, даже если совпадает с названием; 3b — то же плюс метки «Категория: … Бренд: … Цвет: … Описание: …».
- Результат (метрики): 3a — NDCG@10 0.582, Recall@10 0.791, MRR 0.703; 3b — NDCG@10 0.581, Recall@10 0.809, MRR 0.725, Precision@5 0.285, HitRate@10 0.931.
- Вывод: гипотеза подтверждается, и эффект даёт именно разметка полей. 3a значимо меняет только NDCG@10 (+0.004); метки поверх 3a дают Recall@10 +0.018 [0.007; 0.030] и MRR +0.023 [0.007; 0.038]. NDCG@10 при метках не растёт из-за смещения пула в обратную сторону: доля кандидатов с оценкой 1 в топ-10 падает с 24.8% до 20.5%. Структура текста даёт больше, чем смена модели.

**Эксперимент 4. Гибрид поверх шаблона с метками (финальная конфигурация)**
- Гипотеза: эффекты двух изменений складываются — метки улучшают семантику, лексика добавляет точные совпадения по брендам.
- Что меняем: семантическую часть гибрида RRF (`w_sem = 0.8`) на e5-small с метками; лексика и параметры RRF — как в эксперименте 1.
- Результат (метрики): NDCG@10 0.608, Recall@10 0.815, MRR 0.734, Precision@5 0.295, HitRate@10 0.927.
- Вывод: относительно baseline-семантики улучшение значимо по NDCG@10 (+0.029), Recall@10 (+0.025) и MRR (+0.035). Гибрид больше не снижает MRR, но его надбавка поверх семантики с метками значима только по NDCG@10; Recall@10 (+0.006) и MRR (+0.009) — в пределах шума. Гибрид помогает на брендовых запросах (Recall@10 0.968 → 0.977). Конфигурация `hybrid_rrf_w08_labeled` выбрана финальной: лучшие средние Recall@10, MRR и Precision@5, и она не хуже семантики с метками ни по одной метрике.

**Эксперимент 5. Дообучение e5-small (по рекомендации ревью)**
- Гипотеза: e5-small обучена на общих парах «запрос — документ»; дообучение на доменных парах «запрос — релевантный товар» подстроит пространство под язык каталога и поднимет Recall@10 и MRR, прежде всего на описательных запросах без бренда.
- Что меняем: только веса модели. Train разбит по `query_id`: 560 запросов (1 423 пары с relevance ≥ 2) — дообучение, 140 — валидация. MultipleNegativesRankingLoss с in-batch негативами, 3 эпохи, lr 2e-5, батч 32, по одному релевантному товару на запрос за эпоху.
- Результат (метрики, val): семантика — NDCG@10 0.593 → 0.626, Recall@10 0.828 → 0.803, MRR 0.722 → 0.674, HitRate@10 0.943 → 0.900; гибрид — MRR 0.735 → 0.658.
- Вывод: гипотеза отклонена. MRR значимо падает (−0.048 и −0.077), рост NDCG@10 (+0.033) — снова эффект пула. Вероятные причины — мало данных и быстрое переобучение (loss 0.890 → 0.153 за 3 эпохи), лёгкие in-batch негативы из других категорий. Дообученная модель в финал не входит; test повторно не используется.

**Анализ по сегментам.** Бренд в запросе ищется целым словом (31% запросов; подстрокой было 36%). На брендовых запросах метки поднимают MRR (0.839 → 0.881), гибрид — Recall@10 до 0.977. Самый слабый сегмент — описательные запросы без бренда (69%): Recall@10 0.74, MRR 0.67 у лучшей конфигурации.

**5.2. Качественный анализ ошибок** 

Разбор конкретных запросов: где семантический поиск выигрывает, где проигрывает, анализ типичных ошибок (смешение смежных категорий и так далее).

- **Где выигрывает семантика:** описательные запросы и синонимы — «кожаные мокасины» находит «натуральную кожу»; на запросах без бренда Recall@10 0.74 против 0.36 у TF-IDF.
- **Где полезна лексика:** бренды и редкие точные термины — «бриджи зуавы» (TF-IDF ставит товар с оценкой 3 на 2-е место, семантика — на 5-е), брендовые запросы (гибрид поднимает HitRate@10 до 0.991).
- **Ошибки финальной конфигурации** — 25 из 300 запросов test (8.3%) без релевантного товара в топ-10. Типы ошибок:
  1. Атрибут из запроса отсутствует в карточке — «прямые ночные сорочки», «длинные трикотажные лонгсливы»: категория найдена верно, но крой, материал и длина рукава в коротких карточках не указаны.
  2. Неразличимые карточки и шум разметки — «удобные джинсы»: найдены другие джинсы, по тексту не хуже размеченных; «удобство» не описано ни в одной карточке.
  3. Слово-атрибут уводит в соседнюю категорию — «брюки с принтом» (бриджи, футболка с принтом), «джинсовые куртки» (джинсовые шорты на 4–5 местах).
  4. Спорные оценки — «джинсовые куртки»: найденные джинсовые куртки размечены оценкой 1, релевантной считается только мужская укороченная, хотя в запросе нет ни пола, ни фасона.
- Во всех разобранных провалах тип товара определён верно; ошибки — в тонких атрибутах, неоднозначных запросах и разметке.

**Ограничения оценки:** запросы синтетические; разметка пулированная (неразмеченные товары считаются нерелевантными, это занижает метрики семантики — 58% её топ-10 не размечено — и смещает NDCG); каталог оценки 4 256 против 48 376 и текстово богаче (описание у 77.5% против 37.4%); домен ограничен одеждой и обувью; различия порядка 0.01 на 700 и 300 запросах часто незначимы; вес гибрида и конфигурация выбраны на train в роли валидации; скорость и нагрузка не измерялись.

**5.3. Рекомендация бизнесу** 

Стоит ли внедрять векторный поиск? В каком виде: полная замена системы поиска, создание гибрида старого и нового подхода, реранкинг? В каких случаях векторный поиск помогает, а где ошибается?

- **Внедрять стоит:** векторный поиск находит подходящий товар в топ-10 для 90–92% запросов против 60% у поиска по ключевым словам.
- **Главное условие качества — структура карточки:** явные метки атрибутов дали значимый прирост, а более тяжёлая модель и дообучение на имеющейся разметке — нет.
- **Форма — гибрид, а не полная замена:** векторный поиск — основа ранжирования (вес 0.8), поиск по ключевым словам сохраняется как добавка для брендов, артикулов и точных терминов. RRF не требует калибровки скоров и встраивается рядом с текущей системой.
- **Помогает:** синонимы, разговорные и неточные формулировки, поиск по назначению.
- **Ошибается:** тонкие атрибуты, которых нет в карточке (крой, материал, длина рукава); субъективные запросы («удобные»); смежные категории при совпадении атрибута.
- **Порядок внедрения:** A/B-тест на реальном трафике с метриками кликабельности и конверсии поиска.

**5.4. Дальнейшие шаги** 

Что предлагаете делать дальше: попробовать модель на реальных логах запросов, дообучить эмбеддинги? Подумайте, как можно делить данные на выборки без утечки, использовать ANN-индекс при масштабировании, ввести фильтрацию по атрибутам и ввести другие улучшения?

1. Реальные логи запросов и кликов — оценка на реальном распределении и источник обучающих пар: 560 синтетических запросов для дообучения мало (эксперимент 5).
2. Доразметка топа векторного поиска — убрать смещение пула и честно сравнить подходы.
3. Обогащение карточек структурированными атрибутами (пол, сезон, материал, крой) — главный источник ошибок; эксперимент 3 показал, что структура текста даёт больше, чем смена модели.
4. Повторное дообучение на большем объёме пар с разбиением по `query_id`, hard negatives из той же категории и ранней остановкой по валидации — для описательных запросов без бренда.
5. Фильтр или буст по распознанной в запросе категории; фильтры по цвету, бренду, полу поверх векторного поиска.
6. Дедупликация карточек с одинаковым текстом в выдаче.
7. ANN-индекс (FAISS, HNSW) при масштабировании: полный перебор достаточен для десятков тысяч товаров, но не для миллионов.

## 6. Streamlit-приложение

- Функциональность (как поле ввода запроса формирует топ релевантных товаров, что показано по каждому товару): поле ввода запроса, выбор метода (гибрид — финальный, семантический, лексический) и числа товаров (5–30). По каждому товару — название, категория, бренд, цвет, `imt_id`, косинусное сходство e5 и первые 200 символов описания. Поиск идёт по всему каталогу домена — 48 376 карточек.
- Какой пайплайн используется в приложении и как загружаются артефакты (эмбеддинги, индекс): финальная конфигурация `hybrid_rrf_w08_labeled` — RRF из TF-IDF по `product_text` и e5-small по тексту с метками. Артефакты создаются ячейкой в разделе «Финальный тест» ноутбука: `models/e5-small/`, `data/catalog_app.parquet`, `data/emb_app.npy` (строки в одном порядке). Модель и TF-IDF-индекс кешируются через `st.cache_resource`, каталог и эмбеддинги — через `st.cache_data`; для запроса считается только его эмбеддинг.
- Команда запуска (одной командой): `streamlit run app.py`
